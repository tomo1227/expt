# リアクションによる仕様承認

## 状態

保留（ルール整備済み、人のリアクションによる動作確認待ち）

## 目的と仮説

- 目的: 承認時のハッシュとレビュー URL の手入力をなくす。
- 仮説: ハッシュ付きレビューへの人の `+1` を照合すれば、GitHub 標準 UI のリアクション操作で承認できる。
- 対象: ドキュメント・AI プロンプト・Issue/PR テンプレート。
- 対象外: 独自 UI、GitHub Actions の自動起動、機械的な承認ゲート、承認の代行。

## 成功条件

- [ ] 人はレビューへのリアクションで承認でき、ハッシュ転記が不要。
- [x] 仕様不一致、権限不足、削除済み・レビュー編集前のリアクションを無効とする確認手順が一貫している。
- [x] `make check` とプロンプトの構文・リンク検証が成功する。

## 実装と検証の計画

1. 承認の決定箇所であるフローと実装プロンプトをリアクション照合へ変更する。
2. `make check`、YAML frontmatter・相対リンクの検証、GitHub API の読み取りを行う。
3. 人が実際に承認した後の照合は別途実施する。AI はリアクションを追加しない。

## 結果

- `make check`: 成功。開発基盤の設定と差分の検証のみ。
- Ruby の YAML パーサーによるプロンプト・Issue テンプレートの frontmatter と相対リンク検証: 成功。
- `gh api repos/tomo1227/expt/issues/comments/6892167067`: レビュー本文・作成日時・更新日時を取得できた。
- 同コメントの `reactions` API: 取得成功、リアクション 0 件。
- `gh api repos/tomo1227/expt/collaborators/tomo1227/permission`: admin を確認。
- 未検証: 人による追加・削除、リアクション作成日時とレビュー更新日時の照合、権限不足・仕様不一致時の実際の停止動作。
- 判断: 最小の半自動運用として整備。人の操作で検証してから採用判断する。独立した機械的な承認ゲートは未実装。
- 再現方法: 人が上記レビューコメントへ `+1` を付けた後、フロー所定の GET API とハッシュ計算で照合する。承認だけで実装や PR 作成を開始しない。
