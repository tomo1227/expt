# README追記案の要件と計画

## 目的

導入検証として計画したREADMEの追記案を、再承認後に反映・検証するところまでを作業範囲とする。ただし今回の応答で行うのは要件・計画・受け入れ条件の改訂、レビュー、再承認ゲートの提示までであり、README本体は編集しない。

この改訂版は再承認待ちの提案である。旧版への承認は改訂版やREADME編集の許可に流用しない。要件再承認後も、Code Generationの実装計画を提示し、その計画の承認前にREADMEを編集しない。

仮説: 計画のみを依頼して承認前に停止する例を2文示すことで、既存の承認・公開ルールを変えずに導入確認の始め方を明確にできる。

## 作業手順と停止位置

### 今回実行する改訂

- Step 1（FR1・FR2）: 現在のREADMEと既存計画を読み、文案・位置を維持して、反映までを含む要件と制約に改訂する。
- Step 2（FR2・FR3）: この文書の受け入れ条件、質問・確認記録、トレーサビリティを整合させる。
- Step 3（FR2）: 改訂版についてプロダクト責任者のレビューを受け、結果を記録する。AIレビューを人の承認とみなさない。
- Step 4（FR2・FR3）: `make check`、ID整合性、README未変更を検証し、承認対象とintentのパスを示して要件整理の再承認ゲートで停止する。後続工程は実行しない。

### 再承認後に行う予定の反映（今回は未実行）

- Step 5（FR1・FR2）: 人が改訂版を承認した後、Code GenerationでREADMEだけを編集する実装計画と検証手順を作成し、その計画の承認を待つ。
- Step 6（FR1・NFR1）: 実装計画の承認後、READMEの指定位置に上記2文だけを追記する。重複や挿入位置の変化、競合があれば編集せず問題を報告する。
- Step 7（FR1・FR3）: 指定位置・文案の完全一致・1回だけの出現と、追記部分以外の本文が変更前と一致することを確認し、`make check` を実行する。
- Step 8（FR2・FR3）: ローカル変更と検証結果を提示して人の確認を待つ。公開、マージ、デプロイは行わない。

撤回する場合も他の変更を戻さず、この追記の2文だけを対象にする。承認を代行せず、要件・文案・成功条件が再び変わった場合は再レビューと再承認を得る。

## 受け入れ条件

### 今回の再承認ゲート

- AC1（FR1）: 既存READMEを前提に改訂版を開いたとき、1か所・2文の全文、挿入位置、今回と将来の作業手順が特定できる。
- AC2（FR2・NFR1）: 今回の終了時、READMEを含む既存の追跡ファイルに今回の編集差分がなく、変更はintent内の記録に限られる。
- AC3（FR2）: 改訂版のレビュー後、要件整理が再承認待ちであり、今回の人の回答を承認として記録しておらず、Code Generation以降は未実行である。
- AC4（FR2）: 提示された要件・計画、質問・確認記録、トレーサビリティ、レビュー記録、intentの各パスを開ける。
- AC5（FR3・NFR2）: `make check` と整合性検査の実行結果を報告し、実フック実行・承認後再開・README反映後の表示は未検証と明記する。

### 将来の反映完了時

- AC6（FR1・NFR1）: 改訂要件と実装計画の承認後に反映したとき、指定位置に文案が完全一致で1回だけ存在し、2文以外の既存本文、設定、依存関係が変更前と一致する。
- AC7（FR3）: 反映後に文案・位置・重複・既存本文の保持を確認し、`make check` が成功してから結果を報告する。未実施の表示確認やアプリテストを成功と記載しない。
- AC8（FR2・NFR1）: いずれの段階でもブランチ作成、commit、push、PR作成、PR承認、マージ、デプロイを実行しない。
- 境界条件: 改訂依頼だけをREADME編集の許可と読み替えず、今回の再承認ゲートを越えない。文案が既に存在する場合は二重追加しない。
- 異常時: チェック失敗、競合、承認状態の未確認は成功扱いせず、問題を報告して停止する。保護設定は変更しない。

## 制約・対象外

- アプリ実装、アプリ言語・依存の追加、ブランチ作成、commit、push、PR作成、承認代行、マージ、デプロイは行わない。
- README本体は今回変更しない。必要な再承認後の反映対象にのみ含める。既存設定、承認保護、既存の実験記録は引き続き変更しない。
- 外部サービス操作は行わない。今回依頼された改訂版のレビューは実施する。
- 文書計画のみの小さな作業のため、新たな実験記録は作成せず、このintentに計画と結果を残す。
- Copilot Chat履歴の保持は対象外。履歴や保存データ自体は削除せず、Dev Container設定、Dockerfile、makefile、検証スクリプトへの履歴保持用の変更も行わない。

## 検証方法と限界

- `make check`: コンテナJSON、導入スクリプト構文、AI-DLC構成の回帰チェック、追跡ファイルの差分空白検査。
- `git diff --exit-code` と `git diff --cached --exit-code`: 今回、既存の追跡ファイルに作業差分がないことの確認。
- `git hash-object README.md`: 今回の改訂前後でREADMEの内容が同一であることの確認。将来の反映時はその直前の内容を基準とし、追記以外を保持したか比較する。
- 計画の手動照合とJSON整合性検査: FR/NFRのIDがトレーサビリティと一致すること、必要な成果物があることを確認。
- 改訂版のレビュー記録と要件整理の再承認待ちへの移行結果で停止位置を確認する。今回は承認を送信しての後続再開確認を行わない。
- アプリの動作テストは対象外。実際のVS Codeフック実行や承認後再開は、この構成チェックでは検証できない。
- 実行結果は同じディレクトリの [質問・確認記録](requirements-analysis-questions.md) に記載する。
