# README追記の検証手順

## 対象と前提

[実装計画](code-generation-plan.md)と[承認済み要件](../../inception/requirements-analysis/requirements.md)に従い、READMEの2文追記だけを検証する。以下は計画承認後の手順であり、未実施の確認を成功として報告しない。

Unitのない`express`作業のため、READMEを指定したコマンドを使う。`make check`はプロジェクト規約が要求する共通検証として追加実行する。新しいランナー、テストファイル、設定、モック、テストデータ、アプリのカバレッジ測定は非該当。

## Testing Contract

- Methodology: `test-after`
- Ordering: implement each applicable testable layer, then write and run that layer's tests.
- Scope: `express`
- Test Strategy: `Minimal`
- Contract SHA-256: `sha256:faeb535134031441c7d3e78e5dad66bb567886c9e908f821ee79160cd0b662c9`
- 要件ごとに最小の検証を用意し、既存のチェックを成功のまま保つ。アプリのテスト層は存在しないため、文書差分と承認・停止の証跡を確認する。

## 編集前の確認

リポジトリルートで実行する。

```sh
git hash-object README.md
git diff --exit-code -- README.md
git diff --cached --exit-code -- README.md
```

期待結果は、blobが`7a48369934c7c1006489e99093ec221b403d9e8c`で、両方の差分確認が終了コード0。異なる場合はユーザー変更や競合の可能性があるため、編集せず報告する。

本文を確認し、指定の番号付き手順と直後の参照段落が存在し、追記案が未反映であることも確かめる。承認の存在は正規の作業記録で確認し、古い質問ファイルの回答だけを根拠にしない。

## 反映後の要件別確認

### T1: 文案・出現回数・位置（FR1、AC6）

```sh
grep -Fxc -- '導入確認では、`/aidlc READMEへの小さな追記案を計画し、最初の承認ゲートで停止してください。実装・commit・push・PR作成・マージはしないでください。` のように、計画だけを依頼できます。' README.md
grep -Fxc -- '提示された承認対象ファイルと作業記録（intent）のパスを確認し、承認前に停止していることを確かめてください。' README.md
git --no-pager diff --unified=3 -- README.md
```

各`grep`の出力が厳密に`1`であることを確認する。終了コードだけでは回数を保証できない。差分で、番号付き手順の直後、既存の「固定リリース・SHA-256、保存場所…」段落の前に2文が連続していることを確認する。0回、2回以上、順序違い、別位置は不合格。

### T2: 承認と停止（FR2、AC8）

現行要件とこの実装計画について実際の人の承認記録があり、README編集が計画承認後であることを確認する。旧計画の回答を使用せず、結果提示後は人の確認を待つ。ブランチ作成、commit、push、PR作成、承認代行、マージ、デプロイの未実行を結果に記載する。

### T3: 検証結果の正確な記録（FR3、AC7）

```sh
make check
```

終了コード0を要求する。結果記録にT1〜T5と共通検証のコマンド・結果・未検証事項を記載する。失敗や未実施を成功と記載しない。

### T4: 既存本文と変更範囲の保持（NFR1、AC6）

```sh
git diff --numstat -- README.md
git diff --name-only
git diff --cached --exit-code -- README.md
```

READMEの行数差分は追加3行・削除0行を要求する。T1の全文・位置確認と合わせ、追加は指定の2文と空行1行だけであることを差分で照合する。想定外の行が含まれる、既存行が削除・変更される、設定等に今回の差分がある場合は不合格。作業開始前からのユーザー変更は区別し、戻さない。intent内の計画・結果・監査記録の更新はREADME編集とは別の作業記録として扱う。

### T5: 日本語と検証限界（NFR2、AC7）

2文が承認済みの日本語文案と完全一致することをT1で確認する。Markdownの実表示、読者の理解向上、実際のVS Codeフックの動作は別途実施しない限り未検証と明記する。`make check`をアプリのテストや承認フロー全体の動作証明としない。

## 異常時

- 追記済み、挿入位置不明、編集前blob不一致: 編集せず停止する。
- 文案の欠落・重複・位置違い、既存本文の変更: 不合格として原因を確認し、承認範囲内でのみ修正する。
- 共通検証失敗、承認状態の未確認、想定外のユーザー変更との競合: 問題を明示して停止する。保護設定の変更やユーザー変更の取り消しで通過させない。
